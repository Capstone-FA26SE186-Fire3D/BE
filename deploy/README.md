# Fire3D staging on Cloud Run

Prepared infrastructure scripts and workflows; no Google Cloud resources have been provisioned yet. Required: existing Project ID, enabled billing, authenticated gcloud and permission to provision IAM, Cloud Run, Artifact Registry and Secret Manager. Use a dedicated staging project. Default region is asia-northeast1, near the selected Supabase session pooler.

## Bootstrap

1. In Cloud Shell set GCP_PROJECT_ID, GITHUB_REPOSITORY_ID and GITHUB_OWNER_ID (numeric IDs returned by GitHub's repository API), optionally GCP_REGION. Run `bash deploy/setup-gcp.sh` from this repo. This creates two service accounts, Artifact Registry, empty secret containers and GitHub Workload Identity Federation. It grants the deploy account Cloud Run developer at project scope for initial service creation; the runtime account can read only the two named secrets. No service account JSON key is created.
2. Privately add a version to `fire3d-supabase-connection` containing the restricted backend session-pooler connection (not postgres/migration credentials). Add a version to `fire3d-jwt-key` containing a separate base64 random key of at least 32 bytes. Use Secret Manager console or `gcloud secrets versions add NAME --data-file=PRIVATE_FILE --project PROJECT_ID`; do not put secrets in shell arguments, Git, PRs or workflow YAML. The connection should use certificate-verifying TLS after checking the host certificate chain from the deployment environment.
3. Configure the GitHub `staging` environment variables printed by the script, plus DB_SECRET_VERSION and JWT_SECRET_VERSION as numeric secret versions. Configure review/environment protection according to the team's policy. The WIF provider accepts only this numeric repo and owner, develop and the deployment workflow path.
4. Review and merge the task PR into develop. CI builds .NET, executes auth/admin tests on disposable PostgreSQL 17, validates SQL and IFC and builds the container. CD reruns these checks for its exact commit before push/deploy. No hosted schema migration runs automatically. `workflow_dispatch` also requires develop. Main does not deploy automatically.
5. First deployment is IAM-private. Once ready for frontend use, a project administrator can allow invocation explicitly: `gcloud run services add-iam-policy-binding fire3d-api-staging --region REGION --project PROJECT_ID --member=allUsers --role=roles/run.invoker`. Application endpoints still require Fire3D JWT except login and explicitly anonymous endpoints. If organization policy forbids public invocation, retain IAM authentication and use a permitted gateway.
6. Smoke-test `/health/live` (process only), then login -> `/api/auth/me` -> refresh -> logout using the privately stored administrator credentials. Swagger is Development-only and is not exposed on Cloud Run. The hosted database was bootstrapped once; never rerun bootstrap automatically on startup.

## Operations and boundaries

- HTTPS terminates at Cloud Run; Hosting__BehindTlsProxy=true disables application HTTP-to-HTTPS redirects for this deployment. No arbitrary forwarded client IP headers are trusted. Current in-memory IP rate limiting can group clients behind the proxy and is per-instance; review proxy-aware/distributed rate limits before broader use.
- Port 8080, non-root container, 1 CPU / 512 MiB, min 0 / max 2 instances, concurrency 40. Pool size 10 per instance limits typical steady-state DB connections; rolling revisions can overlap. Reassess limits before load tests. Artifact storage/logs/builds may still incur charges; configure a project budget when billing is available.
- IFC is currently a separately tested Python spike, not installed in the API container or a deployed worker. Cloud Run filesystem is ephemeral; future uploads require object storage and processing requires a separately designed worker/job.
- Roll back application traffic to a known previous healthy Cloud Run revision using the console or `gcloud run services update-traffic ... --to-revisions REVISION=100`. Pin numeric secret versions. Application rollback does not undo SQL/data changes; migrations require separate reviewed roll-forward/recovery plans.
- Never use the Supabase owner connection for the deployed application. The current runtime role supports implemented auth/admin only; future domain modules need separately reviewed grants and tenant authorization.

References: [Cloud Run secrets](https://docs.cloud.google.com/run/docs/configuring/services/secrets), [GitHub authentication action](https://github.com/google-github-actions/auth).
